# cann-cann 后续特性展望

本文记录当前新特性实施完成后值得继续规划的方向。这里先明确用户价值、行为边界和前置
依赖，不作为本轮 `04-feature-implementation.md` 的实施范围；正式开发前应再拆分为独立、
可验收的待办清单。

## 1. info 环境信息聚合

提供 Python `environment_info()` 数据对象和 CLI `info` 查询，一次汇总 cann-cann 包版本、
CANN 安装版本及来源、CANN 根目录、主机架构、操作系统、当前 NPU 名称、NPU 架构和各类
核心数量。

- 聚合对象保持只读，并为可能缺失的信息使用 `None`。
- 文本 CLI 使用稳定的 `key: value` 格式，将缺失值展示为 `none`。
- 单项不可用时继续展示其他信息，只有初始化聚合结构本身失败时才整体失败。
- 复用本轮形成的名称解析、`CANNInstallInfo`、环境 API 和 CLI 输出协议。

## 2. doctor 环境诊断

提供 CLI `doctor`，面向“为什么当前环境无法正常使用”而不是单纯展示参数，逐项检查：

- CANN 环境变量及候选根目录。
- 当前架构目录、安装信息文件和平台配置目录。
- ACL 是否可导入、是否能探测 NPU 名称。
- 探测到的 NPU 是否有对应平台配置。
- 关键配置字段是否可读取。

每项应展示成功、警告或失败状态，并在失败时给出可操作建议，例如提示 source 对应的
`set_env.sh`。诊断命令应尽可能完成全部检查，不因前一项失败而过早退出；退出码需要区分
“全部正常”和“存在失败项”。

## 3. JSON 输出

为适合自动化的查询增加全局 `--json` 输出模式，优先覆盖 `info`、`doctor`、`cores` 和
`all-npu-names`，再统一覆盖单值查询。

- JSON 字段稳定使用 snake_case，缺失值使用 JSON `null`。
- 数字保持数字类型，路径和版本使用字符串，不把所有值提前格式化为文本。
- 定义单值、列表、聚合和错误的顶层结构，并在实现前确认是否需要格式版本字段。
- 文本输出继续保持本轮固定的协议，`--json` 不改变 Python API 返回类型。

## 4. 信息来源查询

提供 `--show-source` 或类似能力，帮助用户确认信息来自 ACL、哪个环境变量、哪个平台配置
文件或哪个安装信息文件。

- 来源信息应作为结构化元数据在内部传递，不从错误文本或展示文本中反向解析。
- 普通查询默认保持简洁，仅在用户显式请求时展示来源。
- 与 `info` 和 JSON 模式共同设计，避免之后出现不兼容的输出结构。
- 不输出无关环境变量或可能包含敏感信息的完整进程环境。

## 5. 更友好的未知 NPU 型号错误

当 `resolve_npu_name()` 找不到对应标准配置时，根据当前安装的型号给出少量相近候选，
并提示使用 `all-socs` 查看完整列表。

- 近似匹配只用于错误建议，绝不自动选择或加载相似型号。
- 固定别名已成功展开但目标配置不存在时，同时展示原始输入和展开后的标准目标。
- 候选数量保持较少，并设置相似度门槛，避免错误信息噪声过大。
- Python 异常保留可供程序读取的原始名称、解析后名称和候选列表，CLI 再负责文本格式化。

## 6. 后续规划顺序建议

1. 先完成 `04-feature-implementation.md`，稳定基础数据对象、查询注册表和输出协议。
2. 规划并实现 `info`，验证缺失值和多来源信息的聚合模型。
3. 在同一结构化模型上设计 JSON 和信息来源展示，避免重复调整输出协议。
4. 最后实现 `doctor` 和未知型号建议；二者会复用前述来源数据和分层错误信息。
